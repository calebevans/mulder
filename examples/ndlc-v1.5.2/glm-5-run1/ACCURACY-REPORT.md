## Analysis of Misses and Errors

### Harness errors (items 2, 12, 20)

The PC agent planned the three registry queries the case needs (`USBSTOR`, `TimeZoneInformation`, `CurrentVersion\InstallDate`) in its first extraction batch, with upper-case hive names, and all three failed in `_extract_hive` with `KeyError: 'SYSTEM'` / `KeyError: 'SOFTWARE'`; the model retried them after `run_registry_parser` completed, they failed the same way, and it reported "a fundamental issue with how the registry hives were extracted or how query_registry_value is accessing them". RegRipper output (`registry.system`, 5,209 lines) was indexed and searched for "USBSTOR" without result reaching a finding. Both USB serials, both first-connection times and the timezone were therefore never in the model's hands; items 12 and 20 are MISSED on a harness fault the GLM-4.7 run hit identically, and item 2 lost its edition to a query that asked for `InstallDate` rather than `ProductName`. The RM1 agent's four registry queries were aimed at the RM1 image and failed as expected ("Could not locate system hive in image ... rm1.E01").

### Listed, not read (items 5, 9, 16)

`run_optical_listing` produced the disc's 58 lines and the report reconstructs its sessions from them faithfully; `extract_optical_file` was never called, so no file on the disc was opened, and the content characterisation Kimi run 1 and Opus produced (a federal IT-investment spreadsheet, climate presentations, the Govdocs hyperlinks) is absent. In its place the report reads the carved OMB and LoC strings as the documents themselves (FP 5) and item 16 stays PARTIAL. On the PC, `bulk.url_searches` (155 lines) was indexed and never fetched or searched: the report's only browser evidence is the Drive and iCloud download URLs and a Chrome run count. The search history, the one item every earlier v1.5.2 run above MiniMax delivered, is the report's largest single omission (item 9 MISSED) and the reason its "premeditation" rests on FP 2.

### Seen in-run, not delivered (items 6, 18)

The RM1 agent read all five Secret Project filenames and the `~$ecret_project]_proposal.docx` temp file from RM1's `tsk.filelist` at 04:47:15 and wrote "PROOF the file was OPENED on this USB!"; the findings it submitted an hour later name `[secret_project]_design_concept.ppt` alone and call RM1's content "a small subset". The two files opened from the share (Q28) are in the report at the key's exact times and are presented as PC-side "Secret Project File Access" rather than as share activity; the share itself is reduced to one directory. Neither item changes status for it, but both are thinner than the run's own evidence.

### The setup artefacts and the metadata (FPs 2–5)

Four of the five false positives are the same move: a benign artefact with an exact timestamp is read as an adversary action. The ShimCache modification dates of `Eraser.exe` and `CCleaner64.exe` become executions in January and March; the setup-day accounts become backdoors; the .NET Framework 4 service Eraser's installer registered becomes "Persistence Establishment"; the Govdocs authors' addresses become "theft of federal government data". The alternative-narrative phase planned the right counter-checks for three of them ("legitimate dependency of installed software", "standard IT provisioning", "template OR bibliography OR citation") and changed nothing: findings 14, 16 and 19 sat at inference before and after, and the narrative, the eight conclusion answers, five containment actions and three of five "control failures" carry the persistence subplot unhedged. Findings 5, 6 and 8 show the model half-correcting the fifth (the "IMPORTANT CONTEXT" paragraphs conceding public records) while findings 3 and 10 keep "confirms theft". The DeepSeek v1.5.2 report made the same four claims; the Opus and Kimi reports made only the accounts claim (Kimi) or none of them (Opus).

### CCleaner (item 14)

The series' constant false positive, in its generic form: CCleaner is "executed (clears temp files, registry, browser history)" and the two tools "systematically destroyed evidence". No specific artifact absence is attributed to it, the uninstall three minutes later is not reported, and "closed after doing nothing" remains the one CCleaner fact no run has produced.

### Twenty findings, none deleted; the gate

21 `submit_finding` calls yielded 20 findings and 1 negative; nothing was deleted or merged, so the four extraction agents' output survives intact (the RM2 agent's seven findings account for the OMB/LoC set). The alternative-narrative gate failed twice because the five RM2 findings had no `event_time_start` and the audit tools had not been run; remediation cost 39 turns and 1.6M input tokens, most of them spent trying to read finding IDs from a persisted file ("Cannot extract finding IDs from persisted JSON file without bash/shell access"), before the model stamped the five findings with the RM2 files' mtime range ("2014-12-01T14:50:26 to 2015-03-24T10:00:18") and the gate passed. The report phase then wrote the narrative and passed every gate first time.

### Cost

513 tool calls and 60 minutes sit between Opus (596, 68 min) and Kimi run 1 (827, 52 min); the token profile does not. 9.29M input tokens against Opus's 37K uncached input and Kimi's 197K total: the RM2 extraction session alone consumed 1.65M input, RM3 1.22M, cross-system 1.10M, the gate remediation 1.61M and the counter-analysis 1.0M, with no compactions and no prompt-cache savings visible in the runner's accounting. Whether that is LiteLLM reporting uncached totals for this model or the model re-reading its context each turn, the run is the most expensive in input tokens in the series by more than an order of magnitude.

## Verdict

Run 1 of 3. The 20% / 75% / 25% line sits below Kimi K3's median (35% / 90% / 20%) on every measure and well below Opus (45% / 95% / 10%); against the other open-weight v1.5.2 runs it is above DeepSeek (0% / 60% / 25%) and MiniMax (5% / 60% / 5%) on detection and level with DeepSeek on false positives. The investigative reach is real: four images opened, the masquerade set complete, the disc's session history right, the Mar 25 sequence exact, the insider named by account. The two things that would move it most are the model's, not the harness's: read `bulk.url_searches` (item 9, and the honest basis for "premeditation") and deliver the five filenames the RM1 agent already had (item 6). The harness owes it two items (12, 20) for the upper-case-hive `KeyError`, which has now cost two GLM runs the same registry keys and should be fixed before run 2. The false positives are the more serious problem for a recommended-list decision: five, of which four are the DeepSeek pattern of reading setup artefacts and file metadata as adversary action, carried into containment actions that would disable accounts, block a Microsoft binary and report a government-data theft that did not happen. Runs 2 and 3 will show whether that pattern is the model's habit or this run's.
