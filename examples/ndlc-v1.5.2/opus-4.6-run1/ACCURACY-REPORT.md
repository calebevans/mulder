## Analysis of Misses and Errors

### What the source-name collision cost (items 3, 4, 15; FP 2)

The #228 fix did what it was meant to: `detect_masquerading` returned 17 lines on rm2 (0 in the pre-release run, where the model reconstructed the list from `tsk.filelist.p1`), and the report cites "Sleuthkit masquerade detection confirmed the mismatch". The same evidence then reached the wrong agent. Source names in this build are not qualified by image, and the rm1 agent's first four `get_raw_output` calls (`tsk.partitions`, `tsk.fsstat`, `tsk.filelist`, `tsk.masquerade`, all `after_id: 0`) returned rm2's rows alongside or instead of rm1's. From that point RM1 is "a 4GB USB device with dual partitions", the exFAT stick acquires RM2's FAT32 volume with RM2's Volume ID, and every downstream finding (masquerading, deletion, cross-media table, timeline, containment) carries an "RM1 FAT32" column. The cross-system agent saw the contradiction and edited the wrong finding. The three device items pay for it directly: item 3 loses its FOUND to a wrong device structure and missing serial, item 4 to a missing serial and a volume shared with RM1, item 15 to a deletion "on RM1 FAT32 and RM2" with no deletion time.

### USB identification retrieved, not reported (items 3, 4, 12)

`USBSTOR` was queried in the catalog phase and the catalog summary says "USBSTOR showing SanDisk Cruzer Fit"; the cross-system agent later noted "Only one USBSTOR device registered" (the device-class key, under which both serial subkeys sit). Neither serial, the vendor, the model, RM1's Mar 23 18:31:10Z first connection nor RM2's Mar 24 13:58:32Z first connection appears in the report; the only USB timestamp is the USBSTOR service key's LastWrite (13:37:59Z), attributed to no device. The pre-release run reported all of it (finding 19, "USB Device 1 (likely RM1) ... Serial: 4C530012450531101593&0 ... First registry write: 2015-03-23 18:31:10"). The four status regressions against the pre-release run are these three items plus item 15, and all four are facts the run had in hand.

### CCleaner (item 14)

The same false positive as every run in the series, in a form between the baseline's and the pre-release run's: one artifact class named ("Browser history: 0 windows recovered (consistent with CCleaner clearing browser data)"), plus a new specific: the `Run` key's 15:18:36Z LastWrite is read as CCleaner "removing startup entries", when it is the key's 11:18 EDT uninstall removing CCleaner's own entry. The uninstall, three minutes after launch, is again not narrated; "closed after doing nothing" remains the one CCleaner fact the series has never produced.

### Network drive (item 18) and RM2 opens (item 17)

The share answer is the fullest in the series: UNC path, `V:`, all eight directories with MRU times, the bulk-extractor strings, and, new this run, the two files opened from the share (Q28) tied to the `V:` window at 20:23–20:28Z, and the correct first access "20:23:28Z" in finding 20. What keeps it PARTIAL is the same Mar 22 14:52:22 "first access" in findings 7 and 9 and the narrative, which contradicts finding 20 in the same report. Item 17 likewise has the key's one file (`E:\Secret Project Data\design\winter_whether_advisory.zip`, "explored its ppt\ subdirectory") on the right drive letter in the right window for the first time, and never says which device `E:` was at 14:01.

### OST (item 19)

`spy.conspirator@nist.gov` is named, with two offsets and the display-name form `spy <spy.conspirator@nist.gov>`, downgraded to inference with a counter-analysis note, and blocked in containment. `parse_pst` was never called and `bulk.rfc822` (7,326 lines) was fetched once for five lines; none of the 11 messages is recovered. The pre-release run had the OST path and no correspondent; this run has the correspondent and no messages.

### Registry basics (items 2, 20)

`ProductName` was again never queried (the one `CurrentVersion` query asked for `InstallDate`), so the OS is "Windows 7 64-bit" with the hostname `informant-PC` and no edition, better than the pre-release run's bare "Windows 7". `TimeZoneInformation` reached a finding for the first time in an Opus run (Bias=300, ActiveTimeBias=240, Eastern), and the report then labels every RM2 FAT timestamp "UTC" and never observes the offset; the rm3 agent's "Timestamp offsets (4 hours) consistent with CD burning software using local EDT time" stayed in the run log. Items 2 and 20 are each half of their item, the opposite halves from the pre-release run.

### Format time and drive (item 5)

The disc is identified as a CD-R, dated to the second at both ends of the burn, and reconstructed from both sides; the UDF descriptor timestamp is not stated and no drive is named (`MountedDevices` was not read this time). Neither is contradicted by the key.

### Findings management

40 findings were submitted by the four extraction agents and the cross-system agent; 17 were removed with `delete_finding` ("consolidate the RM1-specific document finding into the cross-media one", "delete the RM2-specific deletion finding") rather than merged, and `deduplicate_findings` was run three times as a dry run and never applied. The consolidation itself cost nothing gradable, since the cross-media findings that replaced the per-device ones carry their content; the pre-release run's `deduplicate_findings` apply, which preserved merged descriptions, is the safer path.
